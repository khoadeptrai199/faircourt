# Backend and database (blueprint §7, §11, §12, §13, §15)

Stack: Java + Spring Boot, REST, one deployable app; PostgreSQL + Flyway; Spring Data JPA for routine CRUD (§7). Exact versions: not chosen yet — propose, get owner approval, pin (§0).

## Code map (§15)

```text
backend/src/main/java/.../faircourt/
  identity/   AccountController, GuestCredentialResolver, AccessPolicy
  sessions/   PublicSessionController, SessionController, SessionService
  players/    AttendanceController, AttendanceService, SkillAssessmentService
  matching/   MatchSuggester, BoardSnapshot, Proposal, ReasonCode
  matches/    HostMatchController, MatchService, MatchRepository
  common/     ApiError, GlobalExceptionHandler, ClockConfig
backend/src/main/resources/db/migration/V1__initial_schema.sql
backend/src/test/.../matching/MatchSuggesterTest.java
backend/src/test/.../api/SessionAccessIT.java
```

- Controller → service → repository. DTOs at the HTTP boundary; domain rules in services / pure matcher; entities stay inside persistence.
- No matching logic in JPA entities or controllers.
- Inject `Clock` for all time-dependent logic (session, token expiry).

## Database (§12)

- Schema: use the SQL in blueprint §12 as `V1`. May split into several files only if dependencies and constraints are preserved.
- UUIDs generated by the backend; all times `timestamptz` in UTC; display in `Asia/Ho_Chi_Minh`.
- Never edit a Flyway migration that has already been applied anywhere — add a new `V<n>__...sql`. Ask the owner before any destructive migration.
- Key DB-level protections — never remove:
  - `ux_busy_court`: one `PLANNED`/`ACTIVE` match per `(session_id, court_no)`.
  - `ux_player_in_unreleased_match`: one unreleased assignment per `(session_id, attendance_id)`.
  - `ux_active_guest_access`: one non-revoked guest credential per attendance.
  - Composite FKs `(id, session_id)` keep attendance/match rows inside their session.

## Application invariants (§12)

`court_no ≤ court_count`; exactly 4 distinct attendance IDs per match, 2 per team; all 4 in the session and `READY` at confirm; no other unreleased match for them; host owns the session; feedback only from a participant after the match finished.

## State machines (§11)

- Attendance: `PENDING → READY`; `READY → ASSIGNED → PLAYING → READY`; `READY ↔ RESTING`; `READY → LEFT`.
  - Members join as `READY`; guests join as `PENDING` until host approval.
  - Cancel planned: `ASSIGNED → READY`. Cancel active: `PLAYING → READY`.
  - Assigned/playing player cannot go `LEFT` until the match is cancelled or finished.
  - Finish: all four → `READY`, `games_played + 1`, `available_since` reset. Waiting players keep their older `available_since`.
- Match: `PLANNED → ACTIVE → FINISHED`; `PLANNED → CANCELLED`; `ACTIVE → CANCELLED`.
- Session `CLOSED`: read-only history, no new assignments.
- No score entry in MVP (§11).

## Transactions (§15)

- `MatchService.confirm / start / finish / cancel` — each a single `@Transactional` method, no partial success.
- Confirm: lock the session row, allocate/increment `next_match_no`, re-read the four attendance rows and the court, validate, insert match + 4 `match_player`, set `ASSIGNED`.
- Finish/cancel: set match state, set `released_at` on all four `match_player`, update attendance — same transaction.
- Never catch a uniqueness violation and pretend success. Map it to `409 MATCH_CONFLICT`.

## API errors (§13)

- Body: `{"code":"MATCH_CONFLICT","message":"A player or court is no longer available.","requestId":"..."}`.
- `400` invalid payload · `401` missing/expired identity · `403` no permission · `404` unknown/not visible · `409` state conflict.
- Validate field lengths and IDs at the boundary. Never return raw exceptions.
- All routes under `/api/v1`; full route list in §13. There is **no** generic "assign player by ID" endpoint (§7).

## Guest questionnaire mapping (§13)

Four answers `serve, rally, movement, positioning`, each 0–3. Either all four scored or all four `null`. Total 0–3 → band 1; 4–6 → 2; 7–9 → 3; 10–12 → 4. All `null` → `current_band = null` (host sees "Unknown / provisional"). This is a pilot heuristic, not a rating.

## Seed (§0)

Local-only, idempotent (restart must not duplicate): one host account `host@faircourt.local` / `FairCourtDemo!1`, one `OPEN` session with 2 courts, **8 READY member players** with varied bands (owner decision 2026-11-09: follow §0, not the 12 in §3/§17; no attendance cap rule). Guests are created only through the real join flow.
