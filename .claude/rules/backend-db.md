# Backend and database (blueprint §7, §11, §12, §13, §15)

Stack: Java + Spring Boot, REST, **microservices** behind a gateway (owner decision 2026-11-17, OD-17; replaces the blueprint's "one deployable app"; see `planning/architecture/system-design.md` and `conventions.md`); PostgreSQL + Flyway, one schema per service; Spring Data JPA for routine CRUD (§7). Pinned (owner-approved 2026-11-09): Java 25, Spring Boot 4.1.2 (Spring Framework 7 / Spring Security 7 — use Boot 4 module starters such as `spring-boot-starter-webmvc`, `spring-boot-starter-flyway`), PostgreSQL 18.6. Base package `com.faircourt`. Run tests with `docker compose --profile test run --rm --build backend-test`.

## Code map

One folder per service under `backend/services/` (`gateway`, `auth-service`, `player-service`, `playmatch-service`; `rating-service` from S05), shared code in `backend/libs/` (`common-web`, `matching`). Table ownership is in `conventions.md`. The blueprint's §15 classes map to services like this: `identity` → gateway + auth-service; `sessions`, `matches` and attendance → playmatch-service; `players` (profiles, assessments) → player-service; feedback → rating-service.

Current code (F18):

```text
backend/pom.xml                                   parent + aggregator (versions pinned here)
backend/libs/matching/      com.faircourt.matching: MatchSuggester, BoardSnapshot, Proposal, ReasonCode, … + MatchSuggesterTest
backend/libs/common-web/    empty until F01
backend/services/gateway/   com.faircourt.gateway: app, security (deny all but health)
backend/services/auth-service/       com.faircourt.auth: security (+ PasswordEncoder), seed; db/migration V1 (schema auth)
backend/services/player-service/     com.faircourt.player: security, seed; db/migration V1 (schema player)
backend/services/playmatch-service/  com.faircourt.playmatch: common (ClockConfig), security, seed, game (PublicGameController, PublicGameQuery, PublicCodeGenerator); db/migration V1 + V2 (schema playmatch)
backend/legacy/V1__initial_schema.sql   old single-app V1, not on any Flyway path (reference only)
```

Each database service sets `spring.flyway.schemas`, `spring.flyway.default-schema`, `spring.datasource.hikari.schema` and Hibernate `default_schema` to its own schema, so unqualified SQL runs in that schema. Tests per service: `<Service>SchemaIT` (tables, seed, backstops) and `SchemaBoundaryTest`.

- Controller → service → repository. DTOs at the HTTP boundary; domain rules in services / pure matcher; entities stay inside persistence.
- No matching logic in JPA entities or controllers.
- Inject `Clock` for all time-dependent logic (game, token expiry).

## Database (§12)

- Schema: the blueprint §12 SQL, split by owning service (`planning/architecture/system-design.md` §4, F18 design §4). Each service has its own `V1__initial_schema.sql` on its own schema. Cross-schema foreign keys are removed and become plain UUID columns; every other constraint and index from §12 stays. Since V2 (2026-11-18, OD-22) the table `play_session` is named `game` and every `session_id` column is `game_id`. Additions approved by the owner: `game.match_format` (`SINGLES`/`DOUBLES`, default `DOUBLES`, OD-20), `game.min_sets` (default 6, 1–20, OD-19), four optional price-per-person columns (`price_male_min_vnd`, `price_male_max_vnd`, `price_female_min_vnd`, `price_female_max_vnd`, OD-18), and `attendance.display_name` (copied from player-service at join). Players' gender is never stored (OD-18).
- UUIDs generated by the backend; all times `timestamptz` in UTC; display in `Asia/Ho_Chi_Minh`.
- Never edit a Flyway migration that has already been applied anywhere — add a new `V<n>__...sql`. Ask the owner before any destructive migration.
- Key DB-level protections — never remove:
  - `ux_busy_court`: one `PLANNED`/`ACTIVE` match per `(game_id, court_no)`.
  - `ux_player_in_unreleased_match`: one unreleased assignment per `(game_id, attendance_id)`.
  - `ux_active_guest_access`: one non-revoked guest credential per attendance.
  - Composite FKs `(id, game_id)` keep attendance/match rows inside their game.

## Application invariants (§12)

`court_no ≤ court_count`; distinct attendance IDs per match by the game's `match_format`: 4 for `DOUBLES` (2 per team, §12), 2 for `SINGLES` (OD-20; teams A/B with 1 player each is proposed in AD-19, not yet approved); all of them in the game and `READY` at confirm; no other unreleased match for them; host owns the game; feedback only from a participant after the match finished.

## State machines (§11)

- Attendance: `PENDING → READY`; `READY → ASSIGNED → PLAYING → READY`; `READY ↔ RESTING`; `READY → LEFT`.
  - Members join as `READY`; guests join as `PENDING` until host approval.
  - Cancel planned: `ASSIGNED → READY`. Cancel active: `PLAYING → READY`.
  - Assigned/playing player cannot go `LEFT` until the match is cancelled or finished.
  - Finish: every player of the match (4 doubles / 2 singles) → `READY`, `matches_played + 1` (`matches_played` is the "sets played" counter, OD-19; named `games_played` before V2), `available_since` reset. Waiting players keep their older `available_since`.
- Match: `PLANNED → ACTIVE → FINISHED`; `PLANNED → CANCELLED`; `ACTIVE → CANCELLED`.
- Game `CLOSED`: read-only history, no new assignments.
- No score entry in MVP (§11).

## Transactions (§15)

- `MatchService.confirm / start / finish / cancel` in `playmatch-service` — each a single `@Transactional` method, no partial success. Game, attendance and matches live in the same schema precisely so this stays one local transaction (system-design §2).
- Confirm: lock the game row, allocate/increment `next_match_no`, re-read the match's attendance rows (4 doubles / 2 singles) and the court, validate, insert match + one `match_player` per player, set `ASSIGNED`.
- Finish/cancel: set match state, set `released_at` on every `match_player` of the match, update attendance — same transaction.
- Never catch a uniqueness violation and pretend success. Map it to `409 MATCH_CONFLICT`.

## API errors (§13)

- Body: `{"code":"MATCH_CONFLICT","message":"A player or court is no longer available.","requestId":"..."}`.
- `400` invalid payload · `401` missing/expired identity · `403` no permission · `404` unknown/not visible · `409` state conflict.
- Validate field lengths and IDs at the boundary. Never return raw exceptions.
- All routes under `/api/v1`; full route list in §13. There is **no** generic "assign player by ID" endpoint (§7).

## Guest questionnaire mapping (§13)

Four answers `serve, rally, movement, positioning`, each 0–3. Either all four scored or all four `null`. Total 0–3 → band 1; 4–6 → 2; 7–9 → 3; 10–12 → 4. All `null` → `current_band = null` (host sees "Unknown / provisional"). This is a pilot heuristic, not a rating.

## Seed (§0)

Local-only, idempotent (restart must not duplicate): one host account `host@faircourt.local` / `FairCourtDemo!1`, one `OPEN` `DOUBLES` game with 2 courts, minimum 6 sets, price per person men 75,000–85,000 VND / women 65,000–75,000 VND, **8 READY member players** with varied bands (owner decision 2026-11-09: follow §0, not the 12 in §3/§17; no attendance cap rule). Guests are created only through the real join flow.

Each service seeds only its own schema (auth: accounts; player: profiles; playmatch: game + attendance). Seed IDs line up across schemas because every service derives them as `UUID.nameUUIDFromBytes("faircourt-demo:<kind>:<n>")` (e.g. `user:host`, `user:3`, `player:3`, `attendance:3`, and `session:1` for the demo game: that key predates the rename and is kept so existing local databases are not seeded twice). The public code is printed by `docker compose logs playmatch-service | grep "public code"`.

## Tests (§7, §17)

- Pure matcher unit tests (see `frontend-matching.md` → Matching engine).
- PostgreSQL-backed integration test (not only in-memory DB): join → suggest → confirm → start → finish.
- Authorization tests per `privacy-auth.md`.
- `409` on unavailable player/court with no partial rows.
- Health: `http://localhost:9090/actuator/health` (gateway) is UP; each database service's own `/actuator/health` (Compose health check) is UP after Flyway + DB connection (§0).
- Schema boundary: every database service keeps its `SchemaBoundaryTest` green (AD-12).
