# Architecture decision log

Status values: `PROPOSED` → `ACCEPTED` (owner, with date) or `REJECTED`. A later decision may `SUPERSEDE` an earlier one; never delete a row.
Details for each decision are in [system-design.md](system-design.md). Product open questions are `OD-xx` in [ROADMAP.md](../ROADMAP.md#5-open-decisions).

| ID | Decision | Status | Affects | Rationale | Design section |
|---|---|---|---|---|---|
| AD-01 | Keep the §15 module packages; a module writes only its own tables via its own service; dependencies point `matches → players → sessions → identity → common`, `matching` depends on nothing | SUPERSEDED by AD-11 (2026-11-17, OD-17) | all backend features | Clear ownership without microservices; no cycles | §3 |
| AD-02 | CQRS-lite: JPA entities for writes; `JdbcClient` read queries that return per-audience response records | PROPOSED | F02, F05, F06, F09, F12 | Privacy by construction; no N+1; entities stay in persistence (§15) | §6 |
| AD-03 | State transitions defined in one enum per state machine; entity methods use it; illegal → 409 `STATE_CONFLICT` | PROPOSED | F07, F10, F11 | §11 rules in one place | §7 |
| AD-04 | One `ApiException` + `ErrorCode` catalog; `GlobalExceptionHandler` plus JSON security entry point / access-denied handler; `requestId` per request in MDC and error body | PROPOSED | F01 and every endpoint | One error shape (§13); frontend maps codes to copy | §9 |
| AD-05 | Caller identity as a sealed `CallerIdentity` (Anonymous / Account / Guest) resolved once per request; guest cookie authenticated by a filter on guest-capable paths. *Amended by AD-14: resolved at the gateway, rebuilt in each service from the identity token* | PROPOSED | F03, F04, F05, F12, F13 | Exhaustive handling; identity never from client IDs (§13) | §5 |
| AD-06 | *(Amended by AD-14: lives in the gateway.)* CSRF stays on; token served by `GET /api/v1/auth/csrf` (body: header name + token); the client keeps it in memory and refetches after login/logout. Token repository choice is decided in the F01 design (D-1) | PROPOSED | F01, F03, F04 | §0 requires a bootstrap route and documented header | §10, F01 design |
| AD-07 | Match commands: one `@Transactional` method each; confirm locks the `play_session` row (`FOR UPDATE`); unique-index violations roll back and map to 409 | PROPOSED | F10, F11 | §12, §15 integrity | §8 |
| AD-08 | Frontend adds `hooks/`, `lib/`, `copy/` folders to the §16 layout; `api/client.ts` is the only `fetch` caller; discriminated-union async state; exhaustive status maps | PROPOSED | F02 and every page | §16 page-state matrix enforced by types; one place for copy review | §10 |
| AD-09 | *(Amended by AD-11: one access matrix per service plus the end-to-end check in F15.)* Privacy tests: one `AccessMatrixIT` (rows per route × caller) and JSON key allowlists for every non-host response | PROPOSED | every endpoint | Mirrors the §3 permission table; catches leaks when DTOs change | §12 |
| AD-10 | `MatchSuggester` stays one concrete pure class; a `MatchingPolicy` strategy interface is introduced only when a second policy is approved | PROPOSED | F09, later L-06 | Avoid speculative abstraction; the snapshot is already the seam | §11, §13 |
| AD-11 | Microservices: `gateway`, `auth-service` (`app_user`, `guest_access`), `player-service` (`player_profile`, `skill_assessment`), `playmatch-service` (`play_session`, `attendance`, `play_match`, `match_player` + `matching` lib), `rating-service` (`match_feedback`, S05). A service reads and writes only its own tables; others call it | ACCEPTED 2026-11-17 | all | OD-17; split by transaction boundary so confirm stays one local transaction | §2, §7 |
| AD-12 | One PostgreSQL container and database, one schema per service, one shared DB user (owner 2026-11-17); Flyway per service on its own schema; no cross-schema FKs or joins; a test per service fails if its SQL mentions another service's schema | ACCEPTED 2026-11-17 | all backend | Ownership without extra containers; with a shared user the boundary is enforced by tests, not by grants | §4 |
| AD-13 | One repo; Maven multi-module under `backend/` (`libs/common-web`, `libs/matching`, `services/<name>`); one Dockerfile with build arg `MODULE`; one `mvn verify` runs everything | ACCEPTED 2026-11-17 | F18 and all | Owner 2026-11-17 (one repo, one folder per service); one pipeline command | §3 |
| AD-14 | Gateway as BFF: the only browser-facing backend; owns the route table (deny by default), account HTTP session, CSRF, guest cookie handling, `requestId`; strips client identity headers; forwards a short-lived identity token that services trust. Technology proposal: Spring Cloud Gateway, servlet (Web MVC) variant; compatibility with Boot 4.1.2 **not verified**, checked before the dependency is pinned | ACCEPTED 2026-11-17 (owner chose Spring Cloud Gateway) | F01, F03, F04 | Cookies and CSRF in one place; services never see browser credentials | §5 |
| AD-15 | Service-to-service calls: synchronous REST on `/internal/v1/**`, never routed by the gateway, short timeouts, no automatic retry of writes; a down dependency → `503 SERVICE_UNAVAILABLE`. Each internal route is listed in its feature design for approval | ACCEPTED 2026-11-17 | F04–F14 | Simplest working option before Kafka | §6, §9 |
| AD-16 | Writes that touch several services are orchestrated by the service that owns the main record, with an explicit compensation step; no distributed transactions (first case: guest check-in, F04) | PROPOSED | F04, F05 | Failure handling stays visible and testable | §7 |
| AD-17 | Kafka deferred until the first consumer (notifications or court map). Event names reserved now: `MatchStarted`, `MatchFinished`, `AttendanceChanged`, `PlayerBandChanged`; when Kafka arrives, publish via a transactional outbox | ACCEPTED 2026-11-17 | later | Owner 2026-11-17: Kafka later, not in S01 | §6 |
| AD-18 | Shared libraries hold plumbing only: `common-web` (error model, request ID, identity token, test support) and `matching` (pure). No entities or business rules in libraries | ACCEPTED 2026-11-17 | all | Avoids a "distributed monolith" through shared code | §3, §12 |
| AD-19 | Singles/doubles (OD-20): `play_session.match_format`; the matcher receives the team size from the snapshot; `match_player` keeps teams A/B with 1 or 2 players each | PROPOSED | F09, F10, F18 | One code path for both formats | §4, §8 |
